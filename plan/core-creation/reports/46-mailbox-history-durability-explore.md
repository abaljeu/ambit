This is a plan, not authority. [42 — Migrate PersistHandlers restore and getEventsSince](plan/core-creation/issues/42-migrate-persisthandlers-restore-and-geteventssince.md) already wrote Event JSON and seeded a mailbox [EventLog](src/Shared/EventLog.fs). ## 1. What “mailbox History” is after SES

There is no mailbox `type History` and no past/future stack on the server. [45 — Contract HistoryEvent, mailbox History, PendingKind, StartActorRequest, and ChangeLog](plan/core-creation/issues/45-contract-historyevent-clienthistory-pendingkind-and-changelog.md) deleted that name. Spoken server history is [EventLog](src/Shared/EventLog.fs): an append-only newest-head `{ events: Ev list; nextId: EventId }` stored in [CoreMailboxBackend](src/Server/Core/CoreMailboxBackend.fs) `MailboxContext.eventLog`. [CoreMailbox.eventHistory](src/Server/Core/CoreMailbox.fs) replies with that whole log. [CoreMailbox.eventsSince](src/Server/Core/CoreMailbox.fs) is `EventLog.since` on the same ref. Poll/Load use a second door, [CoreMailbox.getEventsSince](src/Server/Core/CoreMailbox.fs), which reads persist handlers, not the mailbox ref.

The record is `Ev` in [History.fs](src/Shared/History.fs) (`id`, `submissionId`, `authority`, `commandName`, `body`). `EventBody` is `Change` of Ops, `Undo`/`Redo` of target plus Ops, `ActorStart` of the start request, or `ActorStop` of `focusId` plus `ActorResult`. Old 34b names ActorStarted / ActorFinished are those two bodies. `Ev.ops` and `Ev.isAction` are Some/true only for Change/Undo/Redo. Actor bodies have no Ops, do not apply to the Graph (`Ev.apply` is `Unchanged`), and have no `inverseOps`.

Client past/future is [ClientHistory](src/Shared/ClientHistory.fs), the Emacs Action view in the Browser. Arch and [Event abstraction](plan/core-creation/reports/event-abstraction.md) say it is not persisted and not sent on Poll. [46 — Mailbox History durability](plan/core-creation/issues/46-mailbox-history-durability.md) language “past/future (or EventLog)” is leftover from the retired mailbox two-stack. Implement against EventLog. Do not rebuild a server History module.

[CoreEventDispatch](src/Server/Core/CoreEventDispatch.fs) is the only writer of the mailbox store. `postEvent` admits Change/Undo/Redo, fills name-only Undo/Redo through `EventLog.tryFind` plus `Ev.inverseOps`, applies Graph through `persist.applyEvent` when Ops exist, then `commit`. `actorStart` / `actorStop` mint a lifecycle `Ev` (`EventId.zero` draft, new `submissionId`, empty `commandName`, stamped `authority`) and `commit` the same way. Callers must not `postEvent` Actor bodies; `completeAction` rejects those as “mailbox-generated.”

## 2. What already survives restart

[PersistHandlers](src/Server/Core/CoreMsg.fs) already has `appendEvent` and `getEventsSince`. [CoreEventDispatch.commit](src/Server/Core/CoreEventDispatch.fs) writes the stored `Ev` through `appendEvent` before `EventLog.append` on the mailbox ref. A persist error leaves the mailbox log unchanged (see `ActorStart persist Error does not keep Ev in mailbox log` in [Issue42PersistHandlersTests](tests/Server.Tests/Issue42PersistHandlersTests.fs)).

File persist is [FileAgent](src/Server/Core/FileAgent.fs) plus [EventLogFile](src/Server/EventLogFile.fs). Create opens `SYSTEM/gambol.events`, reads entries oldest-first, and builds `persistedEventLog` with `EventLog.restorePersisted`. Live `appendEvent` appends Event JSON and `EventLog.restore`s that one `Ev` onto the persist copy. `getEventsSince` is `EventLog.since` on that copy.

Db persist is [DbAgent](src/Server/Core/DbAgent.fs) plus [Database](src/Server/Database.fs) table `events` (`event_id`, `submission_id`, `payload`). Load uses `getEventsAfter` ordered `event_id ASC` (oldest-first) then `restorePersisted`. Live `appendEvent` inserts the encoded `Ev` and restores it into `LoadedPersist.eventLog`. `createForTest` with an empty connection string stays in-process only; production `create` / `createWithDataDir` load rows.

Mailbox startup already calls `seedEventLog`: `persist.getEventsSince EventId.beforeAll` then `EventLog.restorePersisted` ([CoreMailboxBackend.makeMailBox](src/Server/Core/CoreMailboxBackend.fs)). [42 — Migrate PersistHandlers restore and getEventsSince](plan/core-creation/issues/42-migrate-persisthandlers-restore-and-geteventssince.md) tests prove a single Change `Ev` comes back on `eventHistory` after File or Db dispose/create, and a lone `EventBody.ActorStart` comes back on File `getEventsSince`. Event JSON already round-trips Actor bodies in [EventJson](src/Shared/EventJson.fs).

File Graph still loads from [DocumentLoader.tryLoadState](src/Server/DocumentLoader.fs) (documents plus [Bookkeeping.readRevision](src/Server/Bookkeeping.fs)). Db Graph still loads from the projection (`graph.revision` via [Database.loadPersistedState](src/Server/Database.fs)). Those checkpoints are Graph persist high-water, not the Poll cursor. `FileAgent.applyEvent` / `DbAgent.applyEvent` apply Ops and reject `Ev has no Ops`. `getEventId` on both agents is `State.eventId`, which today follows last applied Action / meta or projection revision, so after hello (ActorStart, Change, ActorStop) it can sit on the Change `EventId` while EventLog `nextId` is past ActorStop.

Process-lifetime on purpose, and out of this ticket: [CoreActorPool](src/Server/Core/CoreActorPool.fs) live rows and Actor secrets, mailbox [CoreCredentials](src/Server/Core/CoreCredentials.fs) Browser secrets, and [ClientHistory](src/Shared/ClientHistory.fs). [34b — Outside Core lifecycle proof](plan/core-creation/issues/34b-outside-core-lifecycle-proof.md) and [35b — Browser Run hello](plan/core-creation/issues/35b-browser-run-hello.md) may treat EventLog as process-lifetime in their proofs; they already write through File `appendEvent` in-process, but they do not dispose and recreate the host.

## 3. EventLog authority, replay, and one serial

EventLog persist is the authority: File `SYSTEM/gambol.events` and Db table `events`. If a Change/Undo/Redo `Ev` (Ops) is in that log and Graph or projection never applied it, restart/recover re-executes those events onto Graph oldest-first with [Ev.apply](src/Shared/History.fs) (or `ChangeAmendment.applyOps`), then continues. ActorStart/ActorStop still have no Ops — they restore into EventLog only; `Ev.apply` is already `Unchanged` for those bodies. Same-transaction event-plus-Graph write is not the [46 — Mailbox History durability](plan/core-creation/issues/46-mailbox-history-durability.md) durability story (optional later Db hardening; brittle for File and for lifecycle `appendEvent`). Replay-from-log is the road. Live `applyEvent` cannot be that recover path as written: [FileAgent.applyOne](src/Server/Core/FileAgent.fs) / [DbAgent.applyOneEvent](src/Server/Core/DbAgent.fs) skip Graph apply when `submissionId` is already in the persist log, which is true for every restored `Ev`. Recover belongs in File/Db create after both Graph and EventLog are in memory, using the existing Graph checkpoint ([Bookkeeping.readRevision](src/Server/Bookkeeping.fs) / `graph.revision`) to decide which Ops `Ev` ids are still ahead of documents or projection, and as the Poll tip when EventLog is empty/missing or Graph is ahead by eventId.

Alan rejects two disagreeing serial types. One EventId. When EventLog is non-empty and at or ahead of Graph, that number is the EventLog tip: max restored `Ev.id`, equivalently the predecessor of `EventLog.nextId` (`empty.nextId` is 1; [EventLog.tip](src/Shared/EventLog.fs) is `EventId.zero` when there are no events). When EventLog is empty/missing, or Graph `eventId` is ahead of the log, Graph is the sole available authority and `getEventId` / `State.eventId` take the Graph checkpoint. `EventLog.nextId` stays the next assignable id and is not what doors return. Smallest unify: [FileAgent.appendEvent](src/Server/Core/FileAgent.fs) and [DbAgent.appendPersistedEvent](src/Server/Core/DbAgent.fs) set `State.eventId` to the stored `Ev.id` after every successful append (Actor and Action). `PersistHandlers.getEventId` already reads that field, so [CoreMailbox.getEventId](src/Server/Core/CoreMailbox.fs), [Api.getPoll](src/Server/Api.fs) / `postLoad` `eventId`, and [Api.postCommand](src/Server/Api.fs) `latestId` (already `EventId.max` of the returned tail and `persistId`) follow the live tip without a new cursor type. After recover of a non-empty log at or ahead of Graph, set `State.eventId` to that EventLog tip even when the last log row is ActorStop. Empty or Graph-ahead recover keeps the Graph checkpoint. Do not write Actor ids into `gambol.meta` as if they were Graph checkpoints; do not invent `EventId.tip` unless Shared needs the helper for tests.

## 4. Smallest durable cut

Do not add a second log and do not persist ClientHistory. Keep Undo Change-only: `Ev.inverseOps` is None on Actor bodies, [ClientHistory.tryTakeAction](src/Shared/ClientHistory.fs) skips non-Actions, and `completeAction` errors if the Undo target has no inverse Ops. After restore, a name-only Undo of a Change `EventId` must still fill Ops; an Undo aimed at an ActorStart/ActorStop `EventId` must still fail.

Mailbox seed still needs the order fix. [CoreMailboxBackend.seedEventLog](src/Server/Core/CoreMailboxBackend.fs) runs `restorePersisted` on a list that `getEventsSince` already returned newest-head. [EventLog.restore](src/Shared/EventLog.fs) conses and documents oldest-first input. File and Db load paths pass oldest-first file/SQL rows once and are fine. The mailbox seed folds a newest-head tail a second time and reverses it. Single-event 42 tests cannot see that. After a reversed seed, later `EventLog.append` conses onto the wrong end. Adopt the persist `Ev` list as newest-head and set `nextId` past max `Ev.id` without a second cons-fold. Do not change `EventLog.restore`’s oldest-first contract used by [EventLogFile.readAllEvents](src/Server/EventLogFile.fs) and [Database.getEventsAfter](src/Server/Database.fs).

Prove File and Db together: create host, run hello (or stub Pool plus one Change plus `actorStop`), dispose, create again, then assert newest-head `eventHistory` (ActorStop head), the same bodies on `getEventsSince EventId.beforeAll`, `getEventId` equal to the ActorStop `EventId`, and Graph showing the hello child even when documents or projection were behind that Change. A Browser HTTP restart proof is extra, not required: 35b [§7 Browser proof](plan/core-creation/issues/35b-browser-run-hello.md) already runs without 46.

## 5. Risks and open questions

Confirm seed-order with a two-or-three-`Ev` `eventHistory` restart before changing production code. Confirm `applyEvent` submissionId short-circuit with a recover test that has the Change in `gambol.events` / `events` and a Graph checkpoint behind that `EventId`; if create uses `applyEvent`, Graph will not move.

Graph-ahead-of-log (documents persisted, `appendEvent` failed) is the opposite skew. Do not rewrite EventLog from Graph. `getEventId` / `State.eventId` follow the Graph checkpoint until the log catches up. Soft-fail File persist already keeps meta behind the log so startup can recover edits; that is the EventLog-ahead recover case this slice owns.

[EventLogFile.readAllEvents](src/Server/EventLogFile.fs) and Db decode skip bad JSON with `choose`. A corrupt Ops line would not replay. Out of scope unless a test hits it. Do not reopen SES contract tickets. Do not persist the live table or treat restart as Interrupted Actor resume ([Core creation architecture](plan/core-creation/arch.md) Unsettled). Do not cherry-pick Undo. Same-transaction event-plus-Graph is out of scope for this ticket. Db `createForTest` is not a durability seam.
