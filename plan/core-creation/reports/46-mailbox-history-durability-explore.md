This is a plan, not authority. ## 1. What “mailbox History” is after SES

There is no mailbox `type History` and no past/future stack on the server. [45 — Contract HistoryEvent, mailbox History, PendingKind, StartActorRequest, and ChangeLog](plan/core-creation/issues/45-contract-historyevent-clienthistory-pendingkind-and-changelog.md) deleted that name. Spoken server history is [EventLog](src/Shared/EventLog.fs): an append-only newest-head `{ events: Ev list; nextId: EventId }` stored in [CoreMailboxBackend](src/Server/Core/CoreMailboxBackend.fs) `MailboxContext.eventLog`. [CoreMailbox.eventHistory](src/Server/Core/CoreMailbox.fs) replies with that whole log. [CoreMailbox.eventsSince](src/Server/Core/CoreMailbox.fs) is `EventLog.since` on the same ref. Poll/Load use a second door, [CoreMailbox.getEventsSince](src/Server/Core/CoreMailbox.fs), which reads persist handlers, not the mailbox ref.

The record is `Ev` in [History.fs](src/Shared/History.fs) (`id`, `submissionId`, `authority`, `commandName`, `body`). `EventBody` is `Change` of Ops, `Undo`/`Redo` of target plus Ops, `ActorStart` of the start request, or `ActorStop` of `focusId` plus `ActorResult`. Old 34b names ActorStarted / ActorFinished are those two bodies. `Ev.ops` and `Ev.isAction` are Some/true only for Change/Undo/Redo. Actor bodies have no Ops, do not apply to the Graph, and have no `inverseOps`.

Client past/future is [ClientHistory](src/Shared/ClientHistory.fs), the Emacs Action view in the Browser. Arch and [Event abstraction](plan/core-creation/reports/event-abstraction.md) say it is not persisted and not sent on Poll. [46 — Mailbox History durability](plan/core-creation/issues/46-mailbox-history-durability.md) language “past/future (or EventLog)” is leftover from the retired mailbox two-stack. Implement against EventLog. Do not rebuild a server History module.

[CoreEventDispatch](src/Server/Core/CoreEventDispatch.fs) is the only writer of the mailbox store. `postEvent` admits Change/Undo/Redo, fills name-only Undo/Redo through `EventLog.tryFind` plus `Ev.inverseOps`, applies Graph through `persist.applyEvent` when Ops exist, then `commit`. `actorStart` / `actorStop` mint a lifecycle `Ev` (`EventId.zero` draft, new `submissionId`, empty `commandName`, stamped `authority`) and `commit` the same way. Callers must not `postEvent` Actor bodies; `completeAction` rejects those as “mailbox-generated.”

## 2. What already survives restart

[PersistHandlers](src/Server/Core/CoreMsg.fs) already has `appendEvent` and `getEventsSince`. [CoreEventDispatch.commit](src/Server/Core/CoreEventDispatch.fs) writes the stored `Ev` through `appendEvent` before `EventLog.append` on the mailbox ref. A persist error leaves the mailbox log unchanged (see `ActorStart persist Error does not keep Ev in mailbox log` in [Issue42PersistHandlersTests](tests/Server.Tests/Issue42PersistHandlersTests.fs)).

File persist is [FileAgent](src/Server/Core/FileAgent.fs) plus [EventLogFile](src/Server/EventLogFile.fs). Create opens `SYSTEM/gambol.events`, reads entries oldest-first, and builds `persistedEventLog` with `EventLog.restorePersisted`. Live `appendEvent` appends Event JSON and `EventLog.restore`s that one `Ev` onto the persist copy. `getEventsSince` is `EventLog.since` on that copy.

Db persist is [DbAgent](src/Server/Core/DbAgent.fs) plus [Database](src/Server/Database.fs) table `events` (`event_id`, `submission_id`, `payload`). Load uses `getEventsAfter` ordered `event_id ASC` (oldest-first) then `restorePersisted`. Live `appendEvent` inserts the encoded `Ev` and restores it into `LoadedPersist.eventLog`. `createForTest` with an empty connection string stays in-process only; production `create` / `createWithDataDir` load rows.

Mailbox startup already calls `seedEventLog`: `persist.getEventsSince EventId.beforeAll` then `EventLog.restorePersisted` ([CoreMailboxBackend.makeMailBox](src/Server/Core/CoreMailboxBackend.fs)). [42 — Migrate PersistHandlers restore and getEventsSince](plan/core-creation/issues/42-migrate-persisthandlers-restore-and-geteventssince.md) tests prove a single Change `Ev` comes back on `eventHistory` after File or Db dispose/create, and a lone `EventBody.ActorStart` comes back on File `getEventsSince`. Event JSON already round-trips Actor bodies in [EventJson](src/Shared/EventJson.fs).

Graph durability is a different store. File Graph comes from [DocumentLoader.tryLoadState](src/Server/DocumentLoader.fs) (documents plus [Bookkeeping.readRevision](src/Server/Bookkeeping.fs) into `State.eventId`). Db Graph comes from the projection tables. `FileAgent.applyEvent` / `DbAgent.applyEvent` apply Ops and reject `Ev has no Ops`, so Actor lifecycle never touches Graph apply. `getEventId` on both agents is `State.eventId` (last applied Action / meta revision), not `EventLog.nextId`. That split is the arch lock: EventLog is the audit sequence; Graph persist is documents or projection.

Process-lifetime on purpose, and out of this ticket: [CoreActorPool](src/Server/Core/CoreActorPool.fs) live rows and Actor secrets, mailbox [CoreCredentials](src/Server/Core/CoreCredentials.fs) Browser secrets, and [ClientHistory](src/Shared/ClientHistory.fs). [34b — Outside Core lifecycle proof](plan/core-creation/issues/34b-outside-core-lifecycle-proof.md) and [35b — Browser Run hello](plan/core-creation/issues/35b-browser-run-hello.md) may treat EventLog as process-lifetime in their proofs; they already write through File `appendEvent` in-process, but they do not dispose and recreate the host. That is what [46 — Mailbox History durability](plan/core-creation/issues/46-mailbox-history-durability.md) means by “process-lifetime EventLog from 34b/35b stays until this lands.”

## 3. Smallest durable cut

Do not add a second log, do not persist ClientHistory, and do not replay EventLog onto the Graph. Keep Undo Change-only: `Ev.inverseOps` is None on Actor bodies, [ClientHistory.tryTakeAction](src/Shared/ClientHistory.fs) skips non-Actions, and `completeAction` errors if the Undo target has no inverse Ops. After restore, a name-only Undo of a Change `EventId` must still fill Ops; an Undo aimed at an ActorStart/ActorStop `EventId` must still fail.

The missing product behavior is a mailbox EventLog that, after File or Db restart, still holds the hello audit in newest-head order: ActorStart, then the hello Change, then ActorStop (head is Stop). Persist already stores those bodies. [CoreMailboxBackend.seedEventLog](src/Server/Core/CoreMailboxBackend.fs) then runs `restorePersisted` on a list that `getEventsSince` already returned newest-head. [EventLog.restore](src/Shared/EventLog.fs) conses and documents oldest-first input. File and Db load paths pass oldest-first file/SQL rows once and are fine. The mailbox seed folds a newest-head tail a second time and reverses it. Single-event 42 tests cannot see that. After a reversed seed, later `EventLog.append` conses onto the wrong end, so `eventHistory` stays wrong even for new work. Persist `getEventsSince` (HTTP Poll) stays newest-head, which is why production Poll can look healthy while the mailbox audit door does not.

The surgical fix is in the seed, not in File/Db write. Adopt the persist `Ev` list as newest-head and set `nextId` past max `Ev.id` (the `restorePersisted` nextId rule) without a second cons-fold. Do not change `EventLog.restore`’s oldest-first contract used by [EventLogFile.readAllEvents](src/Server/EventLogFile.fs) and [Database.getEventsAfter](src/Server/Database.fs). Do not widen PersistHandlers unless a typed `EventLog` return is cleaner than a one-site seed fix. Do not route Actor `Ev` through `applyEvent`.

Prove File and Db: create host, run the hello lifecycle (or stub Pool plus one Change plus `actorStop`), dispose, create again, then assert `eventHistory.events` newest-head membership and order, the same bodies on `getEventsSince EventId.beforeAll`, and `EventLog.nextId` past the max restored `EventId`. Graph after restart still comes from DocumentLoader or projection, not from Event replay. A Browser HTTP restart proof is extra, not required: 35b [§7 Browser proof](plan/core-creation/issues/35b-browser-run-hello.md) already runs without 46.

## 4. Risks and open questions

The seed-order bug is the one implement must treat as fact unless a new test shows otherwise. Confirm it with a two-or-three-`Ev` `eventHistory` restart before changing production code.

`getEventId` versus EventLog tip is the lock that can widen the ticket. Only [EventLog.append](src/Shared/EventLog.fs) calls `EventId.next`. After ActorStart (id 1), Change (id 2), ActorStop (id 3), File/Db `getEventId` is 2 because `State.eventId` moves only on apply. HTTP `latestId` and Poll cursors that trust `getEventId` can sit behind lifecycle `Ev`. [46 — Mailbox History durability](plan/core-creation/issues/46-mailbox-history-durability.md) asks for audit persist/load, not a cursor redesign. If Alan wants one serial for `getEventId` as well, say so; do not silently move `State.eventId` on Actor bodies.

Two EventLog copies exist: mailbox `eventLog` and File/Db `persistedEventLog`. They stay in sync only when every write goes through `commit` (`appendEvent` then mailbox append) and seed copies persist order. A Graph write that succeeds and an `appendEvent` that then fails can leave documents/projection ahead of EventLog; that is older File/Db behavior, not this slice.

[EventLogFile.readAllEvents](src/Server/EventLogFile.fs) and Db decode skip bad JSON with `choose`. A corrupt lifecycle line disappears from the audit with no mailbox error. Soft-fail Graph persist already keeps meta behind the log so File startup can recover edits; EventLog has no twin repair. Out of scope unless a test hits it.

Do not reopen SES contract tickets. Do not persist the live table or treat restart as Interrupted Actor resume ([arch](plan/core-creation/arch.md) Unsettled). Do not cherry-pick Undo. Db `createForTest` is not a durability seam.
