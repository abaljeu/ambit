## 1. Special-node Parse and Persist axes

A Workspace Node, a Directory Node, and a File Node each carry parse state and persist state. A Normal Node carries neither. The two states are independent. A node can be Unparsed and Unpersisted at the same time. They are informational, not locks. Terms: [GLOSSARY](../../GLOSSARY.md). Detail: [[spec.md]].

1. **Parse state** — Parsed, Unparsed, or PullingFile. PullingFile is memory-only. The column `document_state` stores Parsed or Unparsed only. The stored word for Parsed stays `current`. The stored word for Unparsed stays `unparsed`. On server reboot PullingFile is not true. The code names are `PullingFile` and `pullingFile`. [49 — Rename NoServerFile to PullingFile](issues/49-rename-noserverfile-to-pullingfile.md) renamed the code and did not change when the state is set. The JSON word and the `document_state` column word stay `noServerFile`. A second Load request, `CoreMailbox.mbLoadNode`, can repair a failure to load. Other repairs may come later. Parse cannot repair a file that never came. The parse thread runs when a node is Unparsed. NodeParsed sets Parsed when the node is Unparsed. PullingFile stays PullingFile (§10 **Core loop**).
2. **Persist state** — Unpersisted, or Persisted at a version. The persist thread runs when a node is Unpersisted and Parsed. NodePersisting sets Unpersisted. NodePersisted sets the Persisted version when the written version is current (§10 **Core loop**).
3. **Graph change** — A graph change sets the nearest owning special node Unpersisted. It does not mark ancestors. The write is behind the mailbox. It has no state-change Op.
4. **Document-state events** — These messages change document state. `Op.SetText` and the other content ops stay.

| Event | Kind | Parse state | Persist state |
| --- | --- | --- | --- |
| NodeUploading | Notice | PullingFile. Sets PullingFile in memory. Does not write PullingFile to `document_state`. Does not insert the node. | Unpersisted (`persisted` false) |
| NodeReceived | Notice | Unparsed. Clears PullingFile. | Persisted (`persisted` true) |
| NodeParsing | Notice | Parse started. Does not set Unparsed. Does not push. | unchanged |
| NodeParsed | Notice | Parsed. Sets Parsed when the node is Unparsed. PullingFile stays PullingFile. | unchanged |
| NodePersisting | Notice | unchanged | Unpersisted. Sets Unpersisted. |
| NodePersisted | Notice | unchanged | Persisted version, when the written version is current. An older version leaves Unpersisted. |

`Notice` and `CoreMsg` are the same kind of thing. Both end up on the same event log. `Notice.NodeUploading`, `Notice.NodeReceived`, `Notice.NodeParsing`, `Notice.NodeParsed`, `Notice.NodePersisting`, and `Notice.NodePersisted` are `Notice` cases posted through `CoreMailboxApi.postNotice`. They are not Ops on a Change. The parse thread posts `Notice.NodeParsing` and `Notice.NodeParsed`. The persist thread posts `Notice.NodePersisting` and `Notice.NodePersisted`. `Api.postEvents` posts `Notice.NodeUploading` when it runs the upload Change, and `Notice.NodeReceived` when it runs the incoming-file Change. `LazyLoadReconciliationServer.reconcileReceivedFiles` posts `Notice.NodeReceived` for git Load. `WorkspaceUploadStructure.planStubOps`, `WorkspaceUploadStructure.markPullingFile`, and `WorkspaceUploadStructure.planServerFilePresentOps` stay shared Op-list planners and do not post. `CoreMailboxLoad.applyNotice` applies each message and logs it. The client receives every log message. There is no filter. The client learns of parsing from `Notice.NodeParsing`. The mailbox's direct Unparsed write needs no extra event. The browser updates only its resident Graph. Display reads from that graph. The events name a Workspace Node, a Directory Node, or a File Node. `CoreMailboxLoad` `LoadNode` sets Unparsed and pushes and does not post a Node message. Who posts each `Notice`, the persist stack, the stack pull, the persist version, undo, and non-File create are on Graph change, one rule per step. When [[spec.md]] is met, `Op.SetDocumentState`, `Op.SetPersistState`, and `Op.SetParseState` are not ops. Decision 12 **NodeUnpersisted** in [Message shape](cqrs-messages.md) replaces an Unpersisted `Op.SetDocumentState` with `Notice.NodeUnpersisted`. Decision 15 **Notice has its own door** in [Message shape](cqrs-messages.md): `CoreMailboxApi.postNotice` is the private notice function. Holding that function is the permission. Decision 16 **Order carries its envelope fields** in [Message shape](cqrs-messages.md) places `CoreMsg` orders through `Mailbox.PlaceOrder` of `Order`. Decision 7 **Ask reply** places `CoreMsg` reads through `Mailbox.Ask` of `Query` (`State`, `LastEventId`, `EventsSince`).

Only Core changes files, and only Core changes the graph. The states record which side Core just moved. Other operations set Unparsed and Unpersisted. Workspace lock and per-member persist locks are additional protocol beside the states: §6 Core locking model. Do not invent a Conflicted state. ## 6. Core locking model

Commitment 2026-09-30 (Alan). Axes remain informational drift markers (§1), not locks. The workspace lock and per-member persist locks are additional protocol beside the axes. This section is current truth for Core-revision workers. Claim home: [Parse and persist](doc/current/parse-persist.md) (workspace lock claims). Planned architecture is claimed in [[doc/current/]], and intermediate steps stay on this note.

1. **Unparsed and Unpersisted** — The two directions of drift. Both can be true at once.
   1. **Unparsed** — Information on disk has not been pulled into the graph.
   2. **Unpersisted** — Information in the graph has not been written to disk.
2. **Core alone moves both sides** — Only Core changes files, and only Core changes the graph. The flags record which side Core just moved.
3. **Parse thread** — Runs when a node is Unparsed. On completion it adds `Notice` `NodeParsed` through the private function (§10 **Core loop**). The core loop sets Parsed from `NodeParsed`. Graph change expand renamed `ParseFinished` to `Notice.NodeParsed`. `ParseThread` `finishParse` posts `Notice.NodeParsed`. The same handler sets Parsed. Decision 15 **Notice has its own door** in [Message shape](cqrs-messages.md): `CoreMailboxApi.postNotice` is the private notice function. Holding that function is the permission.
4. **Persist thread** — Runs when a node is Unpersisted and Parsed. On completion it adds `Notice` `NodePersisted` through the private function (§10 **Core loop**). The core loop sets Persisted from `Notice.NodePersisted` of `nodeId`. [46 — Record the persist version](issues/46-record-the-persist-version.md) adds the written version. There is no whole-graph snapshot. [Remove dead snapshot code](#remove-dead-snapshot-code). Decision 5 **SnapshotDone** in [Message shape](cqrs-messages.md) replaces `SnapshotDone` with `Notice.NodePersisted` of `nodeId` and `version`. Decision 15 **Notice has its own door** in [Message shape](cqrs-messages.md): `CoreMailboxApi.postNotice` is the private notice function. Holding that function is the permission.
5. **Other operations** — Set Unparsed and Unpersisted.
6. **Locks** — Prevent race conditions between the parse and persist threads and other operations that access files. Locks are held briefly; only long enough to transfer data. No one holds more than one lock, but aggregate locks exist.
7. **Workspace lock** — An aggregate lock. Announces that member files may change.
   1. **Take** — Waits while member files are already changing.
   2. **Pending** — While the lock is pending, new persist locks for those member files cannot be taken, so a persist cannot start between the announcement and the last in-flight write finishing.
   3. **Drain then pull** — When in-flight member file writes and parse reads have drained, the pull proceeds, the arrived files are marked Unparsed, and the lock releases.
   4. **After release** — Persist of a member then waits until that node is Parsed again.
8. **Per-member persist locks** — Additional protocol beside the axes. While the workspace lock is pending, new per-member persist locks for those member files cannot be taken.
9. **Parse and the workspace lock** — Parse does not take a persist lock. It reads the file. The core loop changes the graph. An in-flight parse of a member is still a use of that file, so the same pending lock drains those reads and holds new ones off until the lock releases. After release, Unparsed is what starts the parse thread.
10. **Unpersisted through pull** — A member can already be Unpersisted when the lock is requested, with no persist lock held yet. The pull still marks it Unparsed. The parse thread then runs, and the core loop brings the new file into the graph while Unpersisted is still set. A later persist can write that graph back over the file that just arrived. This is part of the model.
11. **File read/write backstop** — File read/write is strict buffer to/from. A write that finds the file still being written waits until the file is released, then proceeds. That wait is the filesystem backstop; the locks above are the protocol.
