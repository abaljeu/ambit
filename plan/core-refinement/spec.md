# Document-state events

This spec covers document-state messages for [core-refinement](project.md). The rest of the Core seam stays on [core-refinement architecture](arch.md).

## 1. States

1. **Parse state** — Parsed, Unparsed, or PullingFile. PullingFile is memory-only. The column `document_state` stores Parsed or Unparsed only. The stored word for Parsed stays `current`. The stored word for Unparsed stays `unparsed`. PullingFile is not a stored word. On server reboot PullingFile is not true. `noServerFile` [o] obsolescent and `NoServerFile` [o] obsolescent are the code names until [49 — Rename NoServerFile to PullingFile](issues/49-rename-noserverfile-to-pullingfile.md). That ticket renames the code and does not change when the state is set. A second Load repairs a file that never arrived. Other repairs may come later. Parse cannot repair a file that never came. Terms: [GLOSSARY](../../GLOSSARY.md).
2. **Persist state** — Unpersisted, or Persisted at a version. The column `persist_state` stores it. It is separate from parse state. [36 — Add the persist column](issues/36-add-the-persist-column.md) adds that column. [44 — Apply document state from Node events](issues/44-apply-document-state-from-file-events.md) is blocked by that ticket.
3. **Normal Node** — A Normal Node has no parse state and no persist state.
4. **Both** — A node can be Unparsed and Unpersisted at the same time. The states are informational, not locks.

## 2. Events

| Event | Kind | Parse state | Persist state |
| --- | --- | --- | --- |
| NodeUploading | InMsg | PullingFile. Sets PullingFile in memory. Does not write PullingFile to `document_state`. Does not insert the node. | Unpersisted (`persisted` false) |
| NodeReceived | InMsg | Unparsed. Clears PullingFile. | Unpersisted (`persisted` false) |
| NodeParsing | InMsg | Parse started. Does not set Unparsed. Does not push. | unchanged |
| NodeParsed | InMsg | Parsed. Sets Parsed when the node is Unparsed. PullingFile stays PullingFile. | unchanged |
| NodePersisting | InMsg | unchanged | Unpersisted. Sets Unpersisted. |
| NodePersisted | InMsg | unchanged | Persisted version, when the launch version is current. An older version leaves Unpersisted. |
| Graph change, Undo, Redo, and stored replay | behind the mailbox | unchanged | Unpersisted on the nearest owning special node |

1. **Log** — `InMsg` and `CoreMsg` are the same kind of thing. Both end up on the same event log. `InMsg.NodeUploading`, `InMsg.NodeReceived`, `InMsg.NodeParsing`, `InMsg.NodeParsed`, `InMsg.NodePersisting`, and `InMsg.NodePersisted` are `InMsg` cases posted through `CoreMailboxApi.addInMsg`. They are not Ops on a Change. The parse thread posts `InMsg.NodeParsing` and `InMsg.NodeParsed`. The persist thread posts `InMsg.NodePersisting` and `InMsg.NodePersisted`. `Api.postEvents` posts `InMsg.NodeUploading` when it runs the upload Change, and `InMsg.NodeReceived` when it runs the incoming-file Change. `LazyLoadReconciliationServer.reconcileReceivedFiles` posts `InMsg.NodeReceived` for git Load. `WorkspaceUploadStructure.planStubOps`, `WorkspaceUploadStructure.markNoServerFile` [o] obsolescent, and `WorkspaceUploadStructure.planServerFilePresentOps` stay shared Op-list planners and do not post. `CoreMailboxLoad.applyInMsg` applies each message and logs it. The client receives every log message. There is no filter.
2. **Client** — The client applies every log message. The client learns of parsing from `InMsg.NodeParsing`. The mailbox's direct Unparsed write needs no extra event. The browser updates only its resident Graph. Display reads from that graph.
3. **Special nodes** — These messages name a Workspace Node, a Directory Node, or a File Node. `CoreMailboxLoad` `LoadNode` sets Unparsed and pushes through `markUnparsedThenPush`. It does not post a Node message. A pull add or remove does the same for a Directory Node or Workspace Node: the mailbox handler sets Unparsed and pushes. It does not post NodeParsing. Unparsed is set by the mailbox before a node is on the parse thread. Directory reconcile does not mark existing members Unparsed. `ParseThread` `markUnparsed` is removed as a producer of Unparsed marks in Graph change remove markUnparsed. `Api.postEvents` posts `InMsg.NodeUploading` through `CoreMailboxApi.addInMsg` when it runs the Change from `WorkspaceUploadStructure.planStubOps`, including `WorkspaceUploadStructure.markNoServerFile` [o] obsolescent on an existing node. Those functions stay shared Op-list planners and do not post. The post is Graph change expand. `CoreMailboxLoad.applyInMsg` applies `InMsg.NodeUploading` and logs it. Upload stops the direct PullingFile write in Graph change upload.
4. **Stack pull** — The parse thread's stack puller posts `InMsg.NodeParsing` when it pulls a node. NodeParsing means parse started. It does not set Unparsed and does not push. The persist thread's stack puller posts `InMsg.NodePersisting` when it pulls a node. NodePersisting sets Unpersisted and does not change parse state. The threads do not edit the graph. The post is Graph change stack pull. The Core-loop handler applies each message in Graph change apply. Persist pull waits on Graph change persist stack.
5. **Persist version** — Persist state is Unpersisted, or Persisted at a version. Persist launches with a graph version. NodePersisted sets that Persisted version when the launch version is current. An older version leaves Unpersisted. The persist thread appends NodePersisted to the event log and does not edit the graph. This is Graph change persist version.
6. **Undo, Redo, and stored replay** — Undo, Redo, and stored replay modify the graph, so they set the nearest owning special node Unpersisted. Redo gets the same Unpersisted mark as Undo. Undo and Redo do not write a version. The version check in Graph change persist version leaves that Unpersisted when an in-flight persist finishes with an older version. They do not apply document-state messages from the event log. They do not deal with files. Undo and Redo are Graph change undo. Stored replay is Graph change stored replay.
7. **Upload and non-File create** — `Api.postEvents` runs `Op.NewSpecialNode`, then posts `InMsg.NodeUploading` through `CoreMailboxApi.addInMsg`, then posts `InMsg.NodeReceived` through `CoreMailboxApi.addInMsg` when the file arrives. `Op.NewSpecialNode` stays an Op on the event log and inserts the node. NodeUploading does not insert it and does not write PullingFile to `document_state`. An acceptable alternative, not chosen: the NodeUploading handler puts `Op.NewSpecialNode` on the log. A new Directory Node or Workspace Node is created by `postGraphOnly` or `postChange`. There is no new message for that create. The incoming-file ops come from `WorkspaceUploadStructure.planServerFilePresentOps`. That function stays a shared Op-list planner and does not post. `Api.postEvents` posts `InMsg.NodeReceived` through `CoreMailboxApi.addInMsg`. Reconcile does not post that incoming-file `InMsg.NodeReceived`, and reconcile does not move PullingFile to Parsed. The post order is Graph change expand. `CoreMailboxLoad.applyInMsg` applies `InMsg.NodeUploading` and `InMsg.NodeReceived` and logs them in Graph change apply. `Api.postEvents` posts `InMsg.NodeUploading` through `CoreMailboxApi.addInMsg` and stops the direct PullingFile write in Graph change upload. `Api.postEvents` posts `InMsg.NodeReceived` for an incoming file, and `LazyLoadReconciliationServer.reconcileReceivedFiles` posts `InMsg.NodeReceived` for git Load. Each posts through `CoreMailboxApi.addInMsg` and stops its direct Unparsed write in Graph change arrival. Parse and import stop `Op.SetDocumentState` for the Parsed mark in Graph change parsed producers. `ParseThread.finishParse` posts `InMsg.NodeParsed`.
8. **Graph change** — A graph change sets Unpersisted on the nearest owning special node. It does not mark ancestors. The write is behind the mailbox. It has no state-change Op.
9. **Content ops** — `Op.SetText` and the other content ops stay. `Op.NewSpecialNode` stays.
10. **Document-state Set ops** — When this spec is met, `Op.SetDocumentState`, `Op.SetPersistState`, and `Op.SetParseState` are not ops. No other Set op writes parse state, persist state, or PullingFile. `InMsg.ParseFinished` is renamed to `InMsg.NodeParsed` in Graph change expand. It is the same case. The same handler sets Parsed. `ParseThread` `finishParse` posts `InMsg.NodeParsed`. `InMsg.MarkUnparsed` leaves in Graph change contract. `ParseThread` `markUnparsed` is removed in Graph change remove markUnparsed. `CoreMailboxLoad.markUnparsedThenPush` stays the direct Unparsed write and push.

## 3. Sequence

The path is Graph change on [core-refinement architecture](arch.md). Each step leaves upload, import, undo, redo, stored replay, parse, persist, and client display working.

1. **Expand** — `Api.postEvents` posts `InMsg.NodeUploading` through `CoreMailboxApi.addInMsg` when it runs the upload Change. `Api.postEvents` posts `InMsg.NodeReceived` through `CoreMailboxApi.addInMsg` when it runs the incoming-file Change. `LazyLoadReconciliationServer.reconcileReceivedFiles` posts `InMsg.NodeReceived` through `CoreMailboxApi.addInMsg` for a git-changed file. `WorkspaceUploadStructure.planStubOps`, `WorkspaceUploadStructure.markNoServerFile` [o] obsolescent, and `WorkspaceUploadStructure.planServerFilePresentOps` stay shared Op-list planners and do not post. Import logs NodeParsed. Each post is beside `Op.SetDocumentState`. The post does not set state. Today's write still sets the state. `CoreMailboxLoad.applyInMsg` applies `InMsg.NodeUploading` and `InMsg.NodeReceived` and logs them. `InMsg.ParseFinished` is renamed to `InMsg.NodeParsed`. `ParseThread` `finishParse` posts `InMsg.NodeParsed`. The same handler sets Parsed. Apply is the step that writes the §2 effects for the events that do not yet have a handler.
2. **Persist stack** — The persist stack of nodes and the persist thread stand up. On a successful write the thread posts `InMsg.NodePersisted`. It does not edit the graph. Ticket: [51 — Stand the persist stack](issues/51-stand-the-persist-stack.md).
3. **Stack pull** — The parse thread posts `InMsg.NodeParsing` when it pulls a node. The persist thread posts `InMsg.NodePersisting` when it pulls a node. Persist pull waits on the persist stack. Ticket: [52 — Log stack pulls](issues/52-log-stack-pulls.md).
4. **Change** — Apply adds the Core-loop handlers and leaves producers on their current writes. Apply is blocked by [36 — Add the persist column](issues/36-add-the-persist-column.md). [50 — Upload emits NodeUploading](issues/50-upload-emits-nodeuploading.md), [53 — Arrival and reconcile emit NodeReceived](issues/53-arrival-and-reconcile-emit-nodereceived.md), [54 — Parse and import stop the Parsed Set](issues/54-parse-and-import-stop-the-parsed-set.md), and [56 — Remove ParseThread markUnparsed](issues/56-remove-parsethread-markunparsed.md) each follow Apply. Persist version follows the persist stack. [47 — Undo and redo set Unpersisted](issues/47-undo-and-redo-set-unpersisted.md) and [55 — Stored replay sets Unpersisted](issues/55-stored-replay-sets-unpersisted.md) each follow Apply. Browser apply follows Expand.
5. **Contract** — The document-state Set output leaves. `InMsg.MarkUnparsed` leaves. `InMsg.NodeParsed` stays. Each step points at the graph monad in [core-refinement architecture](arch.md).
