# Parse thread architecture match

Updated: 2026-10-01

This report compares [Parse thread architecture](../arch.md) with the updated Core seam and the event-sourced ops protocol. It is a comparison. It leaves those sources unchanged.

## 1. Verdict

The InMsg names, the one mailbox queue, the axis writers on finish, the Directory Parse body, and the workspace-lock handoff still agree. The comparison finds 2 mismatches: **Parse thread is not an Actor**, and **Directory reconcile Poll meeting**. The comparison finds 3 gaps: **Db agent SnapshotDone**, **SnapshotDone handler**, and **New special node axes**.

## 3. Mismatches

1. **Parse thread is not an Actor** — [Parse thread architecture](../arch.md) §1 Story paths, story path 6 **No Actor after pull**, item 1 **Not an Actor** says "The parse thread is a thread." Story path 17 **Emit Changes**, item 1 **File Change**, says file parse posts ops through `postParseOps`. Item 2 **Graph-only post** says "That post is the existing Graph-only Change door." [Event-sourced ops architecture](../../event-sourced-ops/architecture.md) **Roles** says an Actor is "Anything that produces a Change" and names "the Parse File job". It says "All Actors are the same kind." The classification sentence agrees with [core-refinement architecture](../../core-refinement/arch.md) §7 Vocabulary item 6, "Say **parse thread**, not parse actor." It agrees with [Actors](../../../doc/current/actors.md), "An Actor is a function outside Core" and "Parse thread: a thread." It agrees with [Parse and persist](../../../doc/current/parse-persist.md), "Parse thread: a thread" and "Nobody starts an Actor after pull." Story path 6 item 2 **No new Actor** matches that pull sentence. The disagreement is the Roles classification of the Parse File job.

2. **Directory reconcile Poll meeting** — [Parse thread architecture](../arch.md) §5 Unsettled, item 2 **Changes from directory reconcile** says "How a Directory reconcile meets Poll is open." [Event-sourced ops architecture](../../event-sourced-ops/architecture.md) **Long-running Actors** says "Other Browsers learn of it by polling; there is no completion push." **Accepted conveyance and sequencing pins** says residency product detail, "what a job must emit vs what a Browser must Load," may still be proposed. The poll channel and the absence of a completion push are accepted. The parse-thread sentence calls the Poll meeting open and keeps the accepted channel in that same open item.

## 4. Gaps

1. **Db agent SnapshotDone** — [Parse thread architecture](../arch.md) §1 Story paths, story path 22 **Add InMsg**, names two adders. Item 1 **Parse thread** adds `InMsg` `ParseFinished`. Item 2 **Persist thread** adds `InMsg` `SnapshotDone`. [Mailbox](../../../doc/current/mailbox.md) **Messages** says "The db agent adds this case through the private function when the live-document snapshot finishes. That node is the enclosing workspace of the accepted ops that requested the snapshot." [core-refinement architecture](../../core-refinement/arch.md) §10 Module map, **Core loop**, Uses item 3 **Db agent** says the same add. [Db agent](../../../doc/current/db-agents.md) has no SnapshotDone sentence. The product delta restates who adds `InMsg` and is silent on the db agent.

2. **SnapshotDone handler** — Story path 22 item 3 **Core loop** says "SnapshotDone sets Persisted only through `GraphMutate.setPersistState`." [core-refinement architecture](../../core-refinement/arch.md) §10 **Core loop**, Interface item 5 **Snapshot done**, says `SnapshotDone` "sets that node Persisted through `GraphMutate.setPersistState`, and the same completion stores the snapshot graph as `persistedGraph` when it equals the live graph, clears the in-progress flag, and starts another snapshot when one is needed." State item 2 **SnapshotDone** says "That `NodeId` and the snapshot `Graph option`" and "This case replaces `PersistFinished`." [Mailbox](../../../doc/current/mailbox.md) **Messages** adds "including when the snapshot graph is absent." The parse-thread sentence names the Persisted write and is silent on the payload, the stored snapshot graph, the in-progress flag, and the next snapshot.

3. **New special node axes** — [Parse thread architecture](../arch.md) §2 Module map, **Directory Parse body**, Interface item 2 **Create** says "The body returns ops that create each missing File Node." [core-refinement architecture](../../core-refinement/arch.md) §5 Axis-write mechanics, item 7 **Create special** says "A new special node starts **Unparsed** and **Persisted**." The create interface is silent on those start axes.

## 5. Matches

1. **Product boundary** — The preamble says this note is the Parse product delta. Stacks, axes, locks, and the mailbox stay [core-refinement architecture](../../core-refinement/arch.md). `InMsg` on the one queue stays §10 **Core loop**. That matches the Core note's sole-authority sentence.

2. **InMsg cases and the queue** — Story path 22 **Add InMsg** says the cases are `ParseFinished` and `SnapshotDone`. `InMsg` is not an Op. A private function adds `InMsg`. `CoreMailbox.postEvents` and `CoreMailbox.postGraphOnly` do not carry `InMsg`. §10 **Core loop** and [Mailbox](../../../doc/current/mailbox.md) **Messages** say the same. Those pages say `CoreMsg` has no `SnapshotDone`. The parse-thread architecture cites that home. The superseded name AxisCompletion is absent from the parse-thread architecture.

3. **Axis writers on finish** — The parse thread adds `ParseFinished` and leaves the graph axes unchanged. The core loop sets Parsed through `GraphMutate.setParseState`. PersistState stays unchanged. The persist thread adds `SnapshotDone`. The core loop sets Persisted through `GraphMutate.setPersistState`. `Op.SetPersistState` is not a writer. `Op.SetDocumentState` is not the writer of the parsed axis. Those sentences match §5 items 5 **Persist done**, 6 **Directory Parse done**, and 12 **InMsg** through 14 **Private axes**, §10 Interface items 4 **Parse finished** and 6 **Public post**, and [Mailbox](../../../doc/current/mailbox.md) **Messages**. The persist-thread add is still an open claim on §10 **Persist thread** and on [Mailbox](../../../doc/current/mailbox.md). The parse-thread `[x]` is the cited Core door from the preamble. The words agree.

4. **Directory Parse done** — §2 Module map, Uses item 6 **ParseFinished**, says Directory Parse done adds `InMsg` `ParseFinished` and the core loop sets that Directory Node Parsed only. That matches §5 item 6 **Directory Parse done**. [Parse and persist](../../../doc/current/parse-persist.md) **Parse** says the checked `ParseFinished` add is for File parse. The open Directory sentence on that page says that Directory Node is Parsed only.

5. **Directory Parse body** — Story paths 10 **Directory that is not a Workspace** through 16 **Push when the stack exists**, and the module map, say the body walks every node tied to the Directory File, including nodes below the immediate children, creates missing File Nodes, marks a disk-newer File Node Unparsed, and pushes when the Parse stack exists. A Directory Node that is not a Workspace Node uses the same body. Structure-match uses the tie and the Graph. That matches §5 item 10 **Directory Parse body**, §5 item 8 **Client Load on Directory**, and the open Directory sentence in [Parse and persist](../../../doc/current/parse-persist.md) **Parse**.

6. **Load, pop, and locks** — Client Load on a Directory Node marks that Directory Node Unparsed (§5 item 8 **Client Load on Directory**). Mailbox Load of a File Node stays `dispatchLoad` and stays File-only. A Parsed node skips work (§5 item 11 **Parse stack pop**). Drain, land, mark arrived files Unparsed, and release stay §6 **Core locking model**. The body leaves those locks on Core. Parse leaves the persist lock untaken (§6 item 9 **Parse and the workspace lock**). [Parse and persist](../../../doc/current/parse-persist.md) records the same File door, the same thread, and the same lock shape.

7. **File parse Change** — Story path 1 **Unparsed becomes Graph** and story path 17 **Emit Changes** say `planParseFile` turns disk text into graph ops and `postParseOps` is the graph-only Change door. [Parse and persist](../../../doc/current/parse-persist.md) **Parse** says the same, including the Current mark on an Unparsed File Node. [Workspace graph](../../../doc/current/workspace-graph.md) **Document state** still has `DocumentState` as an implemented axis (`[o]`). [Event-sourced ops architecture](../../event-sourced-ops/architecture.md) **The life of a Change** says a Server-side job hands the Change to the same inner apply. **Long-running Actors** says a long job plans off the apply queue and then sends a message so the queue applies the result.

8. **Server-only file parse** — Story paths 7 **Download leaves Parse on the Server** and 8 **Upload leaves Parse on the Server** say the Browser and the App have no `planParseFile` door. [Parse and persist](../../../doc/current/parse-persist.md) **Parse** says the same.

9. **Discovery and stubs** — §4 Alternative considered, item 2 **Fold into Lazy Load reconciliation**, cites §5 item 3 **Discovery**: Parse is not the discovery tool. [Persistence model](../../../doc/current/persistence-model.md) **Invariants** says a Git receive may submit Changes that create missing Directory and File stubs and that this path does not parse file contents. The Directory Parse body remains the separate §5 item 10 **Directory Parse body** claim.
