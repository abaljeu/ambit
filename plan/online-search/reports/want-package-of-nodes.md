# Want package of Nodes

`Want.compose` builds a `NodeId` list. The Server answers that list with a `childMap` and the child `Node` records. Poll and post-Event carry that pair. The Browser installs the pair with `installWantAnswer`.

## 1. Want list — What a Want lists

1. **Return type** — `Want.compose` returns a `NodeId` list. The return type is not a `Node` list. [Want compose](src/Shared/Want.fs)
2. **Inputs** — The function reads a `Graph`, a `SiteMap`, and the zoom root `NodeId`. [Want compose](src/Shared/Want.fs)
3. **No stored Want** — The module comment says that Want has no durable state. The function does not write a store. [Want compose](src/Shared/Want.fs)
4. **Empty list** — The module comment says that an empty list is allowed. [Want compose](src/Shared/Want.fs)
5. **Included walk** — `compose` starts from `IncludedDescendantIds.throughChildrenOfExpandedNodes` at the zoom root. [Want compose](src/Shared/Want.fs) [Included descendant ids](src/Shared/IncludedDescendantIds.fs)
6. **Walk contents** — The walk returns a flat `NodeId` list. It puts the zoom root first. It walks children when the site entry is expanded. It stops at a folded member and keeps that member id. It does not filter ownership. When the zoom root has no site, the list is that one id. [Included descendant ids](src/Shared/IncludedDescendantIds.fs)
7. **Two child ranks** — `compose` calls `plusChildrenOfEach` two times after the walk. Each call keeps the current ids and appends direct children that are not already in the list. An absent `childMap` key adds no children. [Want compose](src/Shared/Want.fs) [Included descendant ids](src/Shared/IncludedDescendantIds.fs)
8. **Second rank condition** — The second call adds a child only when that parent is already in the list and `GraphChildren.tryGet` returns a child list. An Unloaded parent adds no children. [Included descendant ids](src/Shared/IncludedDescendantIds.fs)
9. **Folded children** — The Want comment says that fold stops the walk and that those children are still wanted. `plusChildrenOfEach` adds the children of a folded member when that member has a `childMap` key. [Want compose](src/Shared/Want.fs) [Included descendant ids](src/Shared/IncludedDescendantIds.fs)
10. **Unloaded filter** — `compose` keeps an id when `GraphChildren.isLoaded` is false. `isLoaded` is true when the id is a key in `childMap`. The `Graph` comment says that an absent key is Unloaded and that a present key, including an empty list, is Loaded. [Want compose](src/Shared/Want.fs) [Graph children](src/Shared/Model.fs)
11. **Loaded members** — `List.filter` runs after the two child ranks. A Loaded id from the walk is not in the final list. The filter keeps a child of that id when the child is Unloaded. [Want compose](src/Shared/Want.fs)
12. **List order** — `List.filter` keeps the order of the two-rank list. `compose` does not call `List.distinct`. [Want compose](src/Shared/Want.fs)
13. **No throttle** — The Want comment says that there is no throttle. The function has no count limit. [Want compose](src/Shared/Want.fs)
14. **No reserved tier** — The module comment says that there is no reserved tier and no Zoom tier. `compose` does not read `reservedParentIds`. The walk still starts at the zoom root. [Want compose](src/Shared/Want.fs) [Visible closure parents](src/Shared/ResidentProjection.fs)
15. **No Node-record test** — `compose` does not test that the id has a `Node` record. It tests the `childMap` key only. [Want compose](src/Shared/Want.fs) [Graph children](src/Shared/Model.fs)
16. **Browser call** — `currentWant` calls `Want.compose` with the view-model graph, the site map, and the zoom root. `currentPollRequest` and `currentChangeRequest` always set `want` from `currentWant`. [Update helpers](src/Client/UpdateHelpers.fs)
17. **Spec context** — `Want.compose` returns Unloaded ids from the included walk and from two child ranks. The browser-residency spec describes that same list. [Want compose](src/Shared/Want.fs) [Browser residency spec](plan/browser-residency/spec.md)

## 2. Answer — What the Server answer contains

1. **Answer pair** — `ResidentProjection.wantAnswer` returns a `childMap` and a `Node` list. [Want answer](src/Shared/ResidentProjection.fs)
2. **Parent ids** — The function uses each Want id as a parent id. It reads that parent with `GraphChildren.tryGet`. [Want answer](src/Shared/ResidentProjection.fs)
3. **Distinct parents** — The function calls `List.distinct` on the Want list before it builds edges. [Want answer](src/Shared/ResidentProjection.fs)
4. **Server does not walk Included** — The included-walk comment says that the Server does not zoom-expand. `wantAnswer` does not call `throughChildrenOfExpandedNodes`. It uses the supplied id list. [Included descendant ids](src/Shared/IncludedDescendantIds.fs) [Want answer](src/Shared/ResidentProjection.fs)
5. **Complete edge** — For one parent, the function looks up a `Node` for every child id. The edge is complete when the `Node` count equals the child count. The function then keeps that parent id, the `ChildNode` list, and those child `Node` records. [Want answer](src/Shared/ResidentProjection.fs)
6. **Omitted edge** — The comment says to omit a parent edge when any target header is absent. The code omits the parent when `tryGet` returns no child list. It also omits the parent when any child id has no `Node`. [Want answer](src/Shared/ResidentProjection.fs)
7. **Empty child list** — A parent whose child list is empty is complete. The edge is that parent and an empty list. That edge adds no `Node` to the node list. [Want answer](src/Shared/ResidentProjection.fs)
8. **Child Nodes** — The node list is the child `Node` records from the complete edges. `List.distinctBy` keeps the first `Node` for one id. The function has no separate step that adds the parent `Node`. [Want answer](src/Shared/ResidentProjection.fs)
9. **One edge rank** — Each `childMap` key is a Want parent id with a complete edge. A child gets a `childMap` key only when that child is also a distinct Want parent with a complete edge. [Want answer](src/Shared/ResidentProjection.fs)
10. **Node order** — The node list follows the distinct Want ids. Inside one edge it follows that child list. [Want answer](src/Shared/ResidentProjection.fs)
11. **Response fields** — `ChangeSuccessResponse` requires `nodes` and `childMap`. The comment says that a missing `nodes` field fails decode. The comment says that an absent `childMap` key stays Unloaded and that an empty list is a Loaded leaf. [Change success response](src/Shared/ApiResponses.fs)
12. **Envelope fields** — The same response also has `eventId`, `buildEpochSec`, `pageBuildEpochSec`, `apiVersion`, `isReady`, `externalChanges`, `events`, optional `message`, and optional `bootstrapHash`. [Change success response](src/Shared/ApiResponses.fs)
13. **Success wire** — `encodeChangeSuccessResponse` writes `nodes` with `encodeNode` and `childMap` with `encodeChildMap`. The cursor key is `r`. The event key is `c`. The other keys are `b`, `p`, `v`, `ready`, and `externalChanges`. `message` and `bootstrapHash` are present only when the option has a value. [Change success wire](src/Shared/ApiResponseSerialization.fs)
14. **Required child map field** — Decode requires the JSON field `childMap`. `decodeChildMap` reads a list of `parent` and `children`. An empty list becomes an empty map. A parent that is not in that list is an absent key. [Change success wire](src/Shared/ApiResponseSerialization.fs) [Child map wire](src/Shared/Serialization.fs)
15. **Node wire** — `encodeNode` writes `id`, `text`, `name`, `cssClasses`, `kind`, `documentState`, `parseState`, `persistState`, and `updateTime`. It does not write `owner`. It does not write `lockPresent`. [Node wire](src/Shared/Serialization.fs)
16. **Child edge wire** — `encodeChildNode` writes `ref` and `id`. The `ref` string is `ref` or `owner`. [Child edge wire](src/Shared/Serialization.fs)
17. **Decode defaults** — `decodeNode` calls `Node.Create` and does not pass `owner` or `lockPresent`. `Node.Create` sets a missing owner to `Guid.Empty` and a missing `lockPresent` to false. [Node decode](src/Shared/Serialization.fs) [Node create](src/Shared/Model.fs)
18. **Want wire** — `encodeWant` writes a JSON list of `NodeId` values. A poll body has `eventId` and `want`. A change body has `events` and `want`. [Want wire](src/Shared/ApiResponseSerialization.fs)
19. **SyncWant type** — `SyncWant` has the field `want`. `encodeSyncWant` writes that field. The Browser encode functions for Poll and post-Event are `encodePollRequest` and `encodeChangeRequest`. [SyncWant](src/Shared/ApiResponses.fs) [Want wire](src/Shared/ApiResponseSerialization.fs) [Update codec](src/Client/UpdateCodec.fs)
20. **Poll answer values** — `postPoll` copies `nodes` and `childMap` from `wantAnswer`. It sets `message` to none and `bootstrapHash` to none. `externalChanges` is true when the event list is not empty. [Poll answer](src/Server/Api.fs)
21. **Change answer values** — `postEvents` copies `nodes` and `childMap` from `wantAnswer`. `events` is the accepted events plus later events. It copies `message` from the accepted result. It sets `bootstrapHash` to none. [Change answer](src/Server/Api.fs)
22. **Sync shape** — `SyncResponse` has `events`, `nodes`, and `childMap`. The comment says that the nodes are Want-answer Nodes and that Load Fetch maps to those fields. `changeSuccessToSync` copies the three fields. [Sync response](src/Shared/ApiResponses.fs) [Sync conversion](src/Shared/SyncLogic.fs)
23. **Spec context** — `wantAnswer` returns child edges and the `Node` records those edges point at. The browser-residency spec describes that same answer. [Want answer](src/Shared/ResidentProjection.fs) [Browser residency spec](plan/browser-residency/spec.md)

## 3. Doors — Which doors carry that package

1. **Poll door** — The Server registers POST `/ambit/poll`. The handler is `Api.postPoll`. The body decodes as `PollRequest`. [Poll route](src/Server/RouteRegistration.fs) [Poll handler](src/Server/Api.fs)
2. **Poll comment** — The `ChangeSuccessResponse` comment names GET `/poll` and POST `/changes`. The registered Poll route is POST `/ambit/poll`. [Change success response](src/Shared/ApiResponses.fs) [Poll route](src/Server/RouteRegistration.fs)
3. **Changes door** — The Server registers POST `/ambit/changes`. The handler is `Api.postEvents`. The body decodes as `ChangeRequest`. [Changes route](src/Server/RouteRegistration.fs) [Change handler](src/Server/Api.fs)
4. **Events door** — The Server registers POST `/ambit/events`. That route calls the same `Api.postEvents`. [Events route](src/Server/RouteRegistration.fs)
5. **Shared answer builder** — `wantAnswerFromHandle` reads the Server graph and calls `ResidentProjection.wantAnswer`. `postPoll` and `postEvents` use that builder. [Answer builder](src/Server/Api.fs)
6. **Browser Poll** — `runPollServer` posts `currentPollRequest` to `/{currentFile}/poll`. `currentFile` is the page path without the first slash. The boot poll posts the same request shape to the same URL form. [Poll effect](src/Client/App.fs) [Boot poll](src/Client/Program.fs) [Update helpers](src/Client/UpdateHelpers.fs)
7. **Browser Changes** — `runSubmitPendingBatch` posts `currentChangeRequest` to `/{currentFile}/changes`. The upload-structure post uses the same URL and the same request function. [Changes effect](src/Client/App.fs) [Workspace sync post](src/Client/UpdateWorkspaceSync.fs) [Update codec](src/Client/UpdateCodec.fs)
8. **Load door** — POST `/ambit/load` does not read a Want list. `postLoad` decodes `LoadRequest.targets`. `wantAnswerForTargets` calls `wantAnswer` with target ids whose `includeWorkspace` is true. `LoadResponse` has `nodes` and `childMap`. [Load route](src/Server/RouteRegistration.fs) [Load handler](src/Server/Api.fs) [Load answer](src/Shared/ResidentProjection.fs)
9. **Load client** — The Browser posts a `LoadRequest` to `/{currentFile}/load`. `loadResponseToSync` keeps `nodes` and `childMap`. `loadResponseToPoll` sets `nodes` to an empty list and `childMap` to an empty map for the poll-outcome check. [Load effect](src/Client/App.fs) [Load conversion](src/Shared/SyncLogic.fs)
10. **State door** — GET `/ambit/state` does not read a Want list. `getState` returns `StateResponse.graph`. For `RootClosure` it calls `visibleClosureGraph`. The comment on `visibleClosureWantAnswer` says that the closure is the same package as `installWantAnswer`. `encodeStateResponse` writes the key `graph`. It does not write the keys `nodes` and `childMap`. [State route](src/Server/RouteRegistration.fs) [State handler](src/Server/Api.fs) [Visible closure](src/Shared/ResidentProjection.fs) [State wire](src/Shared/ApiResponseSerialization.fs)
11. **Command and Cancel** — POST `/ambit/command` and POST `/ambit/cancel` do not call `wantAnswer`. Command nodes come from `nodesForRequest`. Cancel sends an empty node list to `universalFromHandle`. The universal response has `nodes` and `events`. It has no `childMap`. [Command handler](src/Server/Api.fs) [Universal response](src/Shared/ApiResponses.fs)
12. **API version** — `ApiVersion.current` is 13. The comment says that this wire is API version 1.3, with Want plus edges and Nodes on Poll and post-Event. [API version](src/Shared/ApiResponses.fs)
13. **Spec context** — Poll and post-Event carry the Want list and the answer pair above. The browser-residency spec also names Poll, post-Event, and Load Fetch for this package. [Poll handler](src/Server/Api.fs) [Browser residency spec](plan/browser-residency/spec.md)

## 4. Install — What the Browser installs from that answer

1. **Install function** — `installWantAnswer` takes the answer `childMap`, the answer `Node` list, and the current `Graph`. The comment says that it installs Want-answer edges and the Nodes those edges point at. [Install Want answer](src/Shared/ResidentProjection.fs)
2. **Node merge** — The function puts each answer `Node` into `graph.nodes` with `Map.add` on `node.id`. The same id in the graph is replaced by the answer `Node`. [Install Want answer](src/Shared/ResidentProjection.fs)
3. **Replaced lock field** — The answer wire has no `lockPresent` field. `decodeNode` sets `lockPresent` to false. The merge then stores that decoded `Node`. [Node wire](src/Shared/Serialization.fs) [Node create](src/Shared/Model.fs) [Install Want answer](src/Shared/ResidentProjection.fs)
4. **Dangling edge** — The function returns `Error "dangling edge"` when a child id in the new edges is absent from the merged node map. The merged map starts from `graph.nodes`. A child id that is already in `graph.nodes` is not a dangling edge. The answer `Node` list does not have to repeat that child. [Install Want answer](src/Shared/ResidentProjection.fs)
5. **Edge merge** — The function puts each answer `childMap` entry onto the graph `childMap` with `Map.add`. The new list replaces the old list for that parent. A parent key that is not in the answer stays in the graph map. [Install Want answer](src/Shared/ResidentProjection.fs)
6. **Loaded and Unloaded** — The comment says that an absent `childMap` key stays Unloaded. It says that a present key, including an empty list, is Loaded. It says that the same package is idempotent. A present key is a `childMap` key, and `GraphChildren.isLoaded` is that key test. [Install Want answer](src/Shared/ResidentProjection.fs) [Graph children](src/Shared/Model.fs)
7. **New graph** — On success the function returns `Graph.fromNodes` with the same root, the merged nodes, and the merged `childMap`. [Install Want answer](src/Shared/ResidentProjection.fs)
8. **From nodes** — `Graph.fromNodes` calls `ensureRootKind`, `ensureWorkspacesNode`, `ensureSystemNode`, and `ensureTrashNode`. It rebuilds `parentByChild` and `ownerParentByChild`. It sets the root `owner` to the root id. For each other node, it sets `owner` from `ownerParentByChild` when that map has the id. When the map has no id, it keeps `node.owner`. It sets `focus` to none. [Graph from nodes](src/Shared/GraphBuild.fs)
9. **Empty answer** — `graphAfterWant` returns the same graph when `nodes` is empty and `childMap` is empty. It does not call `installWantAnswer` for that answer. [Graph after Want](src/Shared/SyncLogic.fs)
10. **Non-empty answer** — When `nodes` is not empty or `childMap` is not empty, `graphAfterWant` calls `installWantAnswer`. [Graph after Want](src/Shared/SyncLogic.fs)
11. **Preserve pending** — `applyWantPreservingPending` installs the answer on the current graph. The comment says that this path does not rewind pending and does not apply pending again. The comment says that a post acknowledgement uses this path. [Preserve pending](src/Shared/SyncLogic.fs)
12. **Submit install** — `SyncAnswer.applyChangeSuccess` calls `applyWantPreservingPending` with `changeSuccessToSync`. That conversion keeps `nodes` and `childMap`. [Sync answer](src/Client/SyncAnswer.fs) [Sync conversion](src/Shared/SyncLogic.fs)
13. **Full sync install** — `applySyncResponse` applies `response.events` first. When the answer has nodes or a `childMap`, and pending is not empty, it rewinds pending with the inverse ops. It then installs the answer. It then applies the leftover pending again. [Apply sync response](src/Shared/SyncLogic.fs)
14. **Poll install** — The `Loading` case does not apply the poll. The comment says not to apply Poll tails in the `Loading` state. `SyncAnswer.apply` is `applyWantPreservingPending`. A catch-up poll with events calls `consumeCatchUpPoll`, then `SyncAnswer.apply`. `applySyncResponse` runs for `Uploading` or `Parsing` when `stateOpt` is `DataOutdated`, the event list is not empty, and `isAutoSyncBlocked` is false. It also runs for a catch-up poll with no events. It also runs when `stateOpt` is `None`. It also runs for `DataOutdated` when the event list is not empty and `isAutoSyncBlocked` is false. [Poll done](src/Client/Update.fs) [Sync answer](src/Client/SyncAnswer.fs) [Auto-sync block](src/Client/UpdateHelpers.fs)
15. **Poll error** — A failed apply does not replace the model graph. Outside `Loading`, `Uploading`, and `Parsing`, the failed apply assigns `DataOutdated`. The `Uploading` and `Parsing` failure case returns the ready model. That case does not assign `DataOutdated`. [Poll done](src/Client/Update.fs)
16. **Boot install** — A novel boot poll calls `applySyncResponse` and keeps the poll `nodes` and `childMap`. A confirmed boot poll sends `PollDone` with `SyncAnswer.fromChangeSuccess`. That function removes `events` and keeps `nodes` and `childMap`. [Boot poll](src/Client/Program.fs) [Sync answer](src/Client/SyncAnswer.fs)
17. **Load install** — `LoadDone` calls `applyLoadResponse` with the sync copy from `loadResponseToSync`. The refuse test needs an empty event list and a node list that is not empty. It then returns `Error "raced Load answer"` when `hasPendingLocal` is true or the event ids differ. An empty node list does not match that test, even when `childMap` has keys. The other result calls `applySyncResponse`. `LoadDone` sets `hasPendingLocal` when pending is not empty, or when the sync state is `Sending` or `WaitingToRetry`. The success case in this handler does not call `continueAutoWant`. [Load done](src/Client/Update.fs) [Apply load response](src/Shared/SyncLogic.fs)
18. **Next Poll** — `continueAutoWant` starts a poll when the sync response has nodes or a `childMap` and `currentWant` is not empty. That test reads the response. It does not read the install `Result`. `finishAppliedSubmit` calls it after `applyChangeSuccess`, and also when that result is `Error`. `applyIgnoredSubmitAnswer` calls it only for `Ok`. Poll arms call it after a successful apply. [Continue auto want](src/Client/Update.fs) [Update helpers](src/Client/UpdateHelpers.fs)
19. **Spec context** — `installWantAnswer` keeps an absent `childMap` key Unloaded and treats a present key as Loaded. The browser-residency spec describes that same install rule. [Install Want answer](src/Shared/ResidentProjection.fs) [Browser residency spec](plan/browser-residency/spec.md)
