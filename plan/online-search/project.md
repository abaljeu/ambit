## Decisions so far

1. **One spec file** — Both specs live in [spec](spec.md). The Search spec and the Query spec stay separate sections of that file.
2. **No limit syntax** — A query function may stop under `ExprRun.maxMaterialisedAnswers`. The server stops at that cap. That number is 50. This project does not add expression spelling for that stop. The Find and Move cap stays 200.
3. **Actor file** — `src/Server/SearchActor.fs` is the home of the Search Actor and the Query Actor.
4. **Sequence** — tracer-cut.
5. **Node id** — The identity of a result is the NodeId. [04 — Duplicate hit identity](issues/04-duplicate-hit-identity.md). The server list lists each Node id once.
6. **Remote query eval** — Query eval is remote. The Query Actor evaluates on the server. [05 — Query fulfillment while eval stays local](issues/05-query-fulfillment-while-eval-stays-local.md). [14 — Server-side search](plan/expression-language/issues/14-server-side-search.md) is not edited.
7. **Standing locks** — The Find and Move cap of 200, the shared Find and Move Actor, no paging, the trash rules, and Want nodes for hits stay locks. The run evaluation cap is `ExprRun.maxMaterialisedAnswers`. That number is 50. The Query Ref post stays a proposed design for 16 — Insert Refs under the query line.
8. **Shared search algorithm** — One search algorithm serves Find and Move. Step 1: the client algorithm stops at 200 hits. That work is [14 — Cap of 200](issues/14-cap-of-200.md) section 1 **Find and Move**. Step 2: the Search Actor reuses that algorithm. Today [startSearch](src/Shared/ViewModelSearch.fs) and [takeResults](src/Shared/ViewModelSearch.fs) take the search text, the zoom, and the Graph. The reply holds up to 200 hits. One reply and no continuation cursor stay a seam. The query cap is `ExprRun.maxMaterialisedAnswers` and stays on [14 — Cap of 200](issues/14-cap-of-200.md) section 2 **Query cap**. That number is 50. It is blocked by [11 — Server evaluates](issues/11-server-evaluates.md) only. The Find and Move cap stays 200.
9. **Root only** — Alan, 2026-11-13. Both searches start at the zoom root. The client search reads the residency from the zoom root. The server search reads the full database from the zoom root.
11. **Want nodes** — Alan, 2026-10-07. A server reply with Find results includes the found Nodes as Want-fulfillment. Those hit Headers ride in the existing Want answer `nodes` list. [installWantAnswer](src/Shared/ResidentProjection.fs) merges that list. There is no new package. The client adds those nodes to the residency Graph and then lists the hits, including a hit that was absent from the residency before the reply. Move uses that same reply. The Query Ref post stays a proposed design for 16 — Insert Refs under the query line. Claim home: [Want nodes for hits](../../doc/current/want-nodes.md).
